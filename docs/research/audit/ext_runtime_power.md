# External audit: on-robot runtime, power and safety (A1, A2 hardware side, A3, C11)

Date 2026-11-21. Scope: topics (a) to (h). Method: read the repo, then about 35 web fetches/searches and `gh api` checks.
Rule used: a source is VERIFIED only if I fetched the page or read it with `gh api`. Facts taken from a search-result summary
are marked "(search only)". Anything from memory is marked UNVERIFIED. Prices are rough INR estimates (marked est.) unless I saw a listing.

## 0. The five findings that matter most

1. **"All day" is not reachable with the pack alone, and the BOM has no charging path.** The pack is 850 mAh and gives
   27-40 min (`hardware/electronics.md:78-86`); the only charger is a manual off-robot SkyRC E3 (`hardware/BOM.md:46`).
   Comparable pet robots return to a dock by themselves: Anki Vector runs about 25 min active, then goes home (Anki support, search only);
   Sony aibo walks to its station and lies on it (Sony help guide, search only); Petoi Bittle gives under 30 min when running
   (Petoi docs, search only). Pinch's 27-40 min is normal for the class. What is missing is the dock, not a bigger battery.
2. **The HTTP API is open to the whole network and runs as root.** `robot/http_api.py:74` binds `0.0.0.0`; `deploy/pinch.service:12`
   runs as `User=root`; `/stop`, `/say`, `/forget` need no credential (`robot/http_api.py:39-65`). Fix: localhost bind behind Tailscale Serve plus a bearer token; run as a normal user with device groups.
3. **There is no watchdog and no rollback.** `deploy/pinch.service` has `Restart=on-failure` only (line 16): no `WatchdogSec`, no
   hardware watchdog. `deploy/install.sh:15` copies code over `/opt/pinch` in place, so a bad update has nothing to go back to.
   The smallest sound fix is A/B release folders under systemd (section 7).
4. **Control shares one Python process with everything else.** The 50 Hz loop (`DT = 0.02`, `robot/crab_robot.py:26`), the HTTP thread
   (`robot/http_api.py:75`) and, as far as I could see, the mind and senses live in one interpreter. Nothing sets CPU affinity,
   real-time priority or disables garbage collection (grep for `sched_`, `gc.`, `mlock` in `robot/` found nothing). The risk is the GIL
   (Python's one-thread-at-a-time lock), more than the garbage collector. Fix: a separate control process on its own core (section 5).
5. **Bring-up unknowns on the RK3566 are untested, and several are single points of failure:** the BNO055, INA219 and MPR121 share one I2C bus
   (`hardware/electronics.md:100,108,112`); the FE-URT-1 is a CH340-class chip at 1 Mbps (one retailer source); six hardware-PWM overlays on a ZERO 3W;
   and whether a hardware watchdog appears at all.

## 2. Evidence for the code claims

- Power model: `sim/power.py:25-30` sets `COMPUTE_W = 4.0` ("Radxa busy + camera + sensors"), `BUCK_EFF = 0.90`, `USABLE = 0.80`. The table in
  `hardware/electronics.md:80-86` follows from it. It is a model, not a measurement. The compute figure is the biggest unverified term:
  while standing, 4 W of the roughly 7.4 W battery draw is the computer.
- Servo settings written by setup: gains 32/0/0, max input 6.5 V, min 4.0 V, return delay 0 (`hardware/electronics.md:157-160`).
  The register map in code is called `STS3215` and is used for the STS3032 (`robot/feetech_bus.py:48`). rustypot's `sts3215.rs` lists protection registers
  (max temperature 13, max torque 16, protection current 28, protective torque 34, protection time 35, overload torque 36, over-current time 38, torque limit 48) that Pinch never writes (read with gh).
  The STS3032 is rated 4.8-6 V, 4.5 kg.cm at 6 V, operating -15 to 70 C (retailer pages, search only; no Feetech datasheet found), so a 5 V regulator is right.
- Stale comment: `robot/servos.py:29-33` still says the arm servos use a "PCA9685 PWM board", while the design uses six hardware PWM pins
  (`electronics.md` arm table). Harmless, but fix it so nobody wires the wrong thing.
- Control tick: `state()` reads the bus once per 20 ms tick and caches it; `tick()` clamps joints, limits step size, writes, then `hw.wait(DT)` (`robot/crab_robot.py`).
  `robot/backends.py` `_read_bus` falls back from sync read to single reads. Good design.
- Shared I2C: BNO055 (0x28), INA219 (0x40) and MPR121 (0x5A) are all wired to the header's pins 3/5 (`hardware/electronics.md:100,108,112`).

## 3. (a) Power for an all-day pet

**What the references do:**
- Anki Vector: about 25 min active, then it drives to the charger. At low battery, Wi-Fi and voice are disabled so it can focus on finding the dock. The charger needs a clear path, a hard non-reflective surface and to be visible to the robot. Low light strands it (Anki support and a community mod, search only). Lesson: docking fails in the dark and with clutter; plan a fallback.
- Sony aibo ERS-1000: about 120 min standard operation; when low it walks to the station and lies down on it (Sony help guide, search only). Sony asks for a bright room for the station (same lesson).
- Lovot: nest terminals. If the battery is cold it warms the battery first, which can take hours (Groove X support, search only). Lesson: check cell temperature before charging.
- Petoi Bittle: "less than 30 minutes if you keep Bittle running" (docs.petoi.com, search only). Open Duck Mini and Reachy Mini Wireless: no verified runtime found. Loona: no usable figure found, do not cite.

**Realistic duty cycle for Pinch (my arithmetic from the repo's numbers; UNVERIFIED until measured):**
- Usable energy 0.8 x 850 = 680 mAh. Standing and idle cost 1.0-1.1 A, so 36-40 min; trot about 27 min (`electronics.md:82-86`).
- Torque off, lying on the belly, brain awake with Wi-Fi: assume about 2 W total (a guess; the model's 4 W includes the camera and a busy CPU). That is about 0.3 A at the battery, so about 2 h per pack resting.
- Charging at 0.8 A (just under 1C for 850 mAh) takes about 50 min of constant current plus a tail: plan 65-75 min for 20% to full. A cycle of 35 min up and 70 min docked is a 33% active duty cycle: about 3 hours active in a 10-hour owner day, the rest asleep on the dock. Short 20-minute top-ups (about 270 mAh) suit a pet better than full cycles.
- Do not chase capacity. The bay is 57.5 x 30.5 x 18 mm (`electronics.md:12`). A cylindrical Li-ion pair is unlikely to fit a hand-sized body (UNVERIFIED, no CAD checked).

**Where the charger lives (a CAD decision, before the shell is printed):**
- Put the **charger on the dock**, not in the robot. The robot carries two contacts, a reverse-polarity guard, a 2S protection board with balancing and a temperature input, the fuse and the INA219. A charger fault then stays outside the closed 3D-printed shell.
- A balancing protection board lets a plain 8.4 V constant-current/constant-voltage supply charge through only two contacts (no balance lead through the dock). UNVERIFIED which cheap Indian boards really balance: read the listing for "balance" and test with a multimeter.
- Hobby "2S 8.4 V USB-C boost charger" modules exist in India (2 A version, Rytronics listing INR 69; Robu SKUs R175188-R175190, mostly out of stock; search only). They are IP2326-class boost chargers. Listings often do not state balancing, termination accuracy or a temperature input (search only). Fine for a prototype dock **if** the pack has the balancing board; do not trust the module alone.
  The TI BQ25887 is the documented 2S charger with balancing, but it has no power path (search only): the robot cannot run cleanly from the dock supply while charging, so it must sleep on the dock. Plan for that.
- Pouch vs cylindrical cells: only a pouch cell fits. Its risks are swelling and puncture when handled. The BOM rule "never unattended" (`electronics.md:168`) cannot hold for a dock, which is unattended charging by design. Replace it with: 0.4 A charge current (0.5C), a pack temperature sensor, a software time limit, an INA219 sanity check (current must fall at the end of charge), a polyfuse, a flame-retardant dock base. I found no source for thermal-runaway onset temperatures: UNVERIFIED, read the cell maker's datasheet.
- Printed shell heat: PLA softens at 55-60 C, PETG at about 75-85 C (snapmaker and all3dp pages, search only). A closed shell in an Indian summer (35-40 C ambient) with a 3-4 W Radxa and servos can approach 60 C inside. Use PETG or ASA for the shell and the battery bay. The heatsink in the BOM (`BOM.md:55`) is right.

**How a legged robot finds and mates with a dock:**
- Nav2 docking server (fetched): staging pose 0.7 m in front of the dock; detect the dock pose (usually an AprilTag) within 5 s; controlled approach at 50 Hz with a 30 s timeout; stop on contact or when charge current appears; wait up to 5 s for charging; otherwise return to staging and retry up to 3 times. Contact is detected from wheel stall or a distance threshold, charging from battery current above a threshold. Pinch already has both inputs: ArUco detection (`install.sh:13`) and INA219 current. Port the five phases in plain Python; do not install ROS 2 for them.
- Spot docks with a fiducial on the dock and two indexing cones that guide the connector (Boston Dynamics docs, search only). The crab equivalent is a funnel: a printed ramp with side walls that tolerates about +/-10 mm and +/-15 degrees, then four small magnets pull the contacts together.
- The camera is low and fisheye, so the tag must sit on the dock's back wall at camera height and be large (about 40 mm). In the last 100 mm the tag leaves the view; the final step is dead reckoning, the funnel and the charge-current check.
- Infrared beacons (a 38 kHz LED on the dock, a TSOP-type receiver on the robot, est. INR 40) are a second option for dark rooms. UNVERIFIED for this robot; add only if the tag fails in the dark.
- Contacts: spring-loaded pins (pogo probes) rated 2-3 A against brass or copper plates. Keep the dock plates dead until the robot is sensed (a small current through a resistor), so a coin cannot short them.
- Open-source small docks seen (search only, no verifiable stats, not adoptable as code): Hello Robot Stretch funnel dock CAD, a Hackster magnetic-contact dock with SIFT matching, the "Mikey" spring-probe dock with a Pixy camera.

**Idle power:** no STS3032 holding-current figure exists in what I could fetch. Measure it in A2: bus current torque-on standing, torque-off, and one servo blocked at a low torque limit.

## 4. (b) Feetech STS bus practice

- **Rate.** By arithmetic at 1 Mbps (10 bits per byte): a SYNC_READ of 8 bytes from 12 servos is about 12 x 14 = 168 bytes plus the request, about 2 ms of wire time plus each servo's return delay (set to 0, `electronics.md:160`). The code comment agrees with about 2 ms per bus read. A sync write of 12 positions is about 44 bytes, about 0.5 ms. So 50 Hz has 8-10x headroom and 100 Hz is possible. The limit is the USB adapter, not the wire. UNVERIFIED by measurement.
- **USB adapter.** LeRobot waits up to 50 ms per attempt and mentions a 16 ms USB latency timer (motors_bus.py, read with gh). The Open Duck runtime sets `latency_timer=1` through a udev rule for `ftdi_sio` (Open_Duck_Mini_Runtime README, read with gh). **That rule does not apply to Pinch.** One retailer says the FE-URT-1 uses a CH340 and the FE-URT-2 a CH343P with about 3x throughput and up to 4 Mbps (Switch Science listing, search only; Feetech's manual does not name the chip). The `ftdi_sio` latency knob is for FTDI chips. On the real robot, time 1000 sync reads and look at the 99th percentile. If the CH340 gives multi-ms jitter, buy the FE-URT-2, or wire the Radxa's UART to the bus through a half-duplex buffer.
- **Known problems.** Blog posts mirrored from LeRobot report timeouts and checksum errors at 1 Mbps (secondhand, search only). Pinch already retries (`feetech_bus.py:73,115-125`), rides out transient errors with last-good values and stops after 25 failures or 10 stale reads (`backends.py` `MAX_IO_FAILS`, `MAX_STALE`). That is the right pattern. One gap: when a sync read loses a reply the code discards the buffer and falls back to single reads at about 2 ms each (`feetech_bus.py:198-204`, `backends.py` `_read_bus`), so one dead servo can cost 24 ms and overrun a 20 ms tick. Run that fallback only every N ticks.
- **Protection settings.** Pinch writes only gains, voltage limits and return delay (`electronics.md:157-160`). The servos also have temperature, torque and overload registers (list in section 2). Retailer pages say overload protection triggers above 80% of stall torque for 2 s and heat protection near 70 C (search only). One hobbyist reports stripped gears and three burnt servos in LeRobot SO101 arms (hbrobotics Google group, single anecdote, search only). Adopt: a torque limit near 60%, a short protection time, a 65 C temperature limit, and read temperature every second. Verify the addresses on a real STS3032 first (the tables come from the 3215) and handle the EEPROM lock register.
- **Stored-settings pitfall.** Settings live in each servo's EEPROM, so a replaced servo ships with defaults (ID 1, full torque). Add a boot-time check that reads every servo's stored limits and refuses to start, or rewrites them, on a mismatch. The firmware already refuses to start without calibration (`robot/servos.py:84-90`); do the same for servo settings.
- **Code to reuse.** LeRobot's bus is 29k stars and active, and its new backend is rustypot (Rust with Python bindings). Pinch's pure-Python driver is correct but one more thing to own. Keep it while it meets timing; keep rustypot as the swap-in. The Feetech Python SDK (38 stars) is the weakest option.

## 5. (c) Runtime architecture: ONE recommendation

- **ROS 2 is not worth it.** Lyrical Luth (May 2026) is Tier 1 only on Ubuntu 26.04; Debian Trixie and Ubuntu 24.04 are Tier 3 (docs.ros.org, search only). Radxa images are Debian 11/12 and `install.sh` targets Debian 12. Memory cost is dominated by the DDS layer (RA-L node-composition discussion, search only); I found no per-node numbers on a 2 GB board, and rmw_zenoh needs a separate router process. Wrong trade for one 2 GB board that also runs a camera and face models.
- **What comparable projects do:** Open Duck Mini: plain Python on a Pi Zero 2W, 50 Hz policy loop, 20 Hz command loop, ONNX inference, no ROS (`v2_rl_walk_mujoco.py`, read with gh). Reachy Mini: a Python daemon with FastAPI and rustypot (`pyproject.toml`, read with gh; zenoh not listed there). LeRobot: Python, optional Zenoh for remote use (`pyproject.toml:295`).
- **Python at 50 Hz on a Cortex-A55:** a 20 ms budget is generous; a numpy policy should take well under 1 ms (UNVERIFIED on this board). Measured evidence: on a Pi 5 with the standard kernel under stress, worst-case wake-up latency exceeded 9 ms, PREEMPT_RT cut it below 225 us, and the rest is memory contention (Giacomossi, Forsberg, Tomasic, Cürüklü, Cucinotta, arXiv 2604.19275, ETFA 2026, fetched). LITHE (Lim and Clites, arXiv 2603.07442, IROS 2026 submission, fetched) runs a Python brain beside a C++ 1 kHz loop with isolcpus and lock-free IPC and reports under 4 us release jitter for the real-time side. No source I found measured `gc.freeze` at 50 Hz; measure it yourself.
- **Recommendation (one):** keep Python and split into **three processes** on the one board, with control on its own core:
  1. `pinch-control` (50 Hz): bus sync read/write, IMU, battery, numpy policies, safety checks, watchdog kick. `isolcpus=3` on the kernel command line plus `CPUAffinity=3`, `CPUSchedulingPolicy=fifo` priority 50, `mlockall`, and `gc.collect(); gc.freeze(); gc.disable()` after start-up, with preallocated arrays. No camera, no network inside it.
  2. `pinch-mind` (cores 0-2): camera, faces, audio, the mind, the face screen, the laptop link.
  3. `pinch-api`: the HTTP gateway (section 8).
  IPC: Zenoh in peer mode (eclipse-zenoh/zenoh 3359 stars, pushed 2026-11-20; zenoh-python 177 stars, pushed 2026-11-20), so the same bus reaches the laptop with no new code. Fallback if the aarch64 wheel or memory is a problem: stdlib `multiprocessing.shared_memory` for the 50 Hz state plus a Unix socket for commands. I did not verify a Debian 12 aarch64 wheel or its RAM: UNVERIFIED, test first. A PREEMPT_RT kernel is optional: try `isolcpus` first and measure jitter.
- dora-rs (4100 stars, Apache-2.0, pushed 2026-11-21) and LCM (1211 stars, LGPL-2.1, pushed 2026-11-01) are alternatives. Neither is needed.

## 6. (d) The BNO055 on a Linux board

- **Clock stretching.** The BNO055 holds the I2C clock line low for a long time (Bosch community thread, search only). The Raspberry Pi's I2C hardware mishandles this; Adafruit's fix is to drop the bus to 10 kHz or use a bit-banged driver (Adafruit guide, search only). I found nothing on Rockchip boards, so the RK3566 controller's behaviour is **UNVERIFIED**. Pinch makes it worse by putting the BNO055, INA219 and MPR121 on one bus: a stretched transaction blocks the others and the loop. Fix: move the BNO055 to its own bus, or use its UART mode (Open Duck's code has the UART lines commented out). Test: 10 000 reads at 50 Hz, count errors.
- **Rate and lag.** In fusion mode the chip outputs at 100 Hz, so a 50 Hz read is fine. The fused gravity vector is filtered inside the chip and so lags real tilt. I found no source giving the lag. Measure it (shake test against a reference) and add it to the twin's sensor model (piece B4).
- **Calibration.** Open Duck's runtime saves accelerometer, gyro and magnetometer offsets from an NDOF run (`raw_imu.py`, read with gh). Pinch uses IMU mode, which needs no magnetometer (right: the shell magnets would disturb it, `backends.py:309-311`), but the gyro offset still matters. The code does not save or restore offsets. Add: store the offsets after calibration, restore them at boot, and check gyro bias with the robot still.
- **What comparable robots feed their policies.** Open Duck Mini feeds a BNO055 in `IMUPLUS_MODE` at the control frequency (`imu.py`, read with gh): the same as Pinch. I found no source comparing BNO085 or ICM-42688 for legged policies. The BNO085 has its own I2C problems and gave worse heading in one user's test (search only). Do not switch.
- **What a gravity-and-turn-rate policy needs:** a unit gravity vector and angular rate in the body frame, with a known delay. Pinch's `read()` returns exactly that (`backends.py:335-336`). Verdict: confirmed. Open items: the bus, the delay model, the offset restore.

## 7. (e) Update and rollback: the smallest sound design

- RAUC (1286 stars), SWUpdate (1906), Mender (1250) and OSTree (1706) all do A/B root filesystems and are active. They need bootloader integration and a partition layout the stock Radxa image does not give, and they are built for fleets. systemd's own boot assessment needs systemd-boot and EFI variables (systemd.io, search only), which a U-Boot ZERO 3W lacks. Too much for one robot.
- **Design (my recommendation, not copied from a project):**
  - `/opt/pinch/releases/<git-sha>/` plus a symlink `/opt/pinch/current`. `install.sh` unpacks into a new folder, runs `robot/selftest.py` there, then flips the symlink. Keep the last 3 releases. Calibration and memory already live in `/var/lib/pinch` (`servos.py:19-21`, `install.sh:55-56`), so they survive.
  - `pinch.service`: `Type=notify`, `WatchdogSec=5`; the control loop calls `sd_notify("WATCHDOG=1")` on each good tick; `OnFailure=pinch-rollback.service` points `current` at the previous release and restarts. Keep the existing start limit (`pinch.service:7-8`).
  - Hardware watchdog: `RuntimeWatchdogSec=15` in systemd's `system.conf`. The RK3566 family has a Synopsys DesignWare watchdog in the kernel bindings (search only), but no source confirmed it is enabled on the ZERO 3W. Check `ls /dev/watchdog*` and `wdctl` on the real board; if missing, enable the node with a device-tree overlay.
  - Safe mode: after N failed starts, `pinch-safe.service` holds torque off, shows an error on the face and keeps only the API up. Never boot into walking after a crash loop.
  - Read-only or overlay root and volatile journald, so a power loss cannot corrupt the SD card. A battery brown-out is the likeliest cause of SD corruption: shut down cleanly at 6.8 V (`systemctl poweroff`) and do not rely on the 6.4 V software stop alone.

## 8. (f) Securing the local API

- Today: no authentication, `0.0.0.0`, root; `/stop`, `/say`, `/touch`, `/forget` open (`robot/http_api.py:39-65,74`; `pinch.service:12`). Anyone on the Wi-Fi can make the pet speak to its mind, erase its memory or stop it.
- What others do: Reachy Mini serves FastAPI from its daemon (pyproject, read with gh); I could not verify its authentication. Tailscale Serve (docs, search result) terminates TLS on the tailnet, **removes identity headers a client sends** and sets `Tailscale-User-Login` for tailnet traffic. The docs warn the backend must listen on localhost only or anyone could forge the header. Funnel traffic and tagged devices get no identity header.
- Smallest sound design: (1) bind `127.0.0.1`; (2) `tailscale serve` exposes it to the owner's devices and the laptop; (3) the handler checks `Tailscale-User-Login` against an allowlist, and scripts use a bearer token from `/etc/pinch.env` (mode 600), compared with `hmac.compare_digest`; (4) read-only routes (`/status`) apart from write routes; (5) `/stop` always works with the token, `/forget` needs a confirmation field; (6) cap the request body (`Content-Length` is read with no limit, `http_api.py:36`, so a huge value exhausts RAM); (7) run as a non-root user in groups `dialout`, `i2c`, `gpio`, `audio`, `video`. Mutual TLS is more than a one-robot hobby needs.

## 9. (g) Language and speech models

- **Not on the RK3566.** The rknn-llm README lists RK3588, RK3576 and RK3562 as supported platforms (read with gh). RK3566 is absent, so the 0.8 TOPS NPU stays vision-only. sherpa-onnx has an RKNN path (16074 stars, pushed 2026-11-21, Apache-2.0); its README names RK3588; RK3566 UNVERIFIED.
- **CPU-only LLM:** llama.cpp (135898 stars, MIT) runs on 4 x A55, but with 2 GB shared with the camera and face models only a 0.5B-class 4-bit model fits, at single-digit tokens per second (UNVERIFIED, not measured). It would also fight the control loop for memory bandwidth, which arXiv 2604.19275 names as the residual jitter source. Not worth it.
- **Verdict (confirmed):** the laptop stays an optional higher brain with graceful fallback (`install.sh:42-47`). Without the laptop, a pet that never speaks needs a few dozen commands and its name: a small offline recogniser with a closed word list. Candidates: Vosk (alphacep/vosk-api, 15278 stars, pushed 2026-10-15, Apache-2.0) or sherpa-onnx keyword spotting; wake word openWakeWord (2963 stars, last push 2025-12-30, Apache-2.0). None tested on this board: measure CPU and RAM first. Keep the mind's rules in code and let the laptop only add free-form understanding.

## 10. (h) Independent safety layer

- **Today:** joint limits, step clamp, shin-vs-hip link, arm collision guard, low voltage, bus sag and stale servo checks all run inside `CrabRobot.tick()` and `_check_health()` (`robot/crab_robot.py:170`), in the same process as the code they protect. A hang or exception in the loop disables them with it. The HTTP `/stop` also goes through that process (`http_api.py:64`).
- **References.** The classic Simplex architecture (a trusted simple controller plus a decision module that switches when the complex controller looks unsafe) is still used because the safe part stays small enough to verify while the learned part stays opaque. Neural Simplex (Phan et al., arXiv 1908.00528, 2020) is the learned-controller version; I did not fetch it, and it is older than the window. Recent quadruped work in the same spirit: *Runtime Learning of Quadruped Robots in Wild Environments* (HA-Teacher), Cai, Mao, Sha, Cao, Caccamo, arXiv 2503.04794, 2025, a physics-model backup controller for a deep-RL student, tested on a Unitree Go2 **in Isaac Gym simulation only** (fetched); and *Gameplay Filters: Robust Zero-Shot Safety through Adversarial Imagination*, Nguyen, Hsu, Yu, Tan, Fisac, arXiv 2405.00846, 2024, a full-order safety filter reported on two quadruped platforms (fetched). I found no 2022-2026 small-legged-robot supervisor with released code. Neither method fits a 2 GB board directly; the principle (a small, separate, simple monitor) does.
- **Design for Pinch (smallest).** A guard thread inside the same process shares the GIL, so it is not independent. Use layers that survive a Python hang: (1) the systemd and hardware watchdogs (section 7); (2) servo-side protection written into each servo's EEPROM (section 4), which still works if the Pi dies; (3) the 2S protection board cutting off a flat pack; (4) the low-voltage buzzer (`BOM.md:48`). The STS bus has no heartbeat timeout that I know of (UNVERIFIED), so a killed process leaves torque on. `pinch.service` uses SIGTERM, which sits the robot down cleanly (`pinch.service:19-21`), but SIGKILL or power loss does not: add `ExecStopPost=` running a one-shot `torque_off` script.
- **Servo protection numbers (retailer pages, search only):** overload above 80% of stall for 2 s; heat protection about 70 C; operating range -15 to 70 C. Plan: warn at 55 C, slow the gait at 60 C, torque off and rest at 65 C. Temperature is already in the sync read (`feetech_bus.py:211-212`).
- **People pick it up.** Dangers: pinched fingers in leg gaps, a fall off a desk, a hot belly. Mitigations: detect lift with the IMU and the feet-down sense, then go torque-off within about 100 ms; the five cliff sensors already guard desk edges (`electronics.md:21`); keep leg-to-body gaps either wide or very narrow (the usual finger-pinch guidance; UNVERIFIED, no standard fetched); cap servo torque so a pinch is not harmful; keep belly surface temperature under about 45 C.
- **Heat in a closed shell:** use PETG or ASA, the BOM heatsink, and a software throttle on the Radxa (read `thermal_zone0` every 10 s, drop camera rate above 70 C). Measure with a thermocouple inside a sealed prototype at 35-40 C ambient before the full order.

## 11. Recommended runtime and power design

- **Power:** keep the 2S 850 mAh pack. Add a contact dock: two spring-pin contacts on the belly or rear, two plates on the dock, a funnel and magnets, an AprilTag on the dock's back wall. The charger sits on the dock (CC/CV 8.4 V, 0.4-0.8 A, USB-C 5 V in). The pack carries a balancing protection board with a temperature sensor; the robot carries a polyfuse and a reverse guard; the INA219 confirms charge current. Docking is a port of Nav2's five phases in plain Python. Rest is torque off, belly down, brain at a low rate; shut down cleanly at 6.8 V. Day plan: about 35 min active, about 70 min docked, 20-minute top-ups allowed.
- **Runtime:** Debian and systemd; three Python processes (control on an isolated core with SCHED_FIFO and the collector disabled; mind; API); Zenoh peer mode for IPC and the laptop link; A/B release folders with `WatchdogSec`, `OnFailure` rollback, a safe-mode unit and the hardware watchdog; API behind `tailscale serve` with a token and a non-root user; servo EEPROM protection written and verified at boot.
- **Safety:** four independent layers (watchdogs, servo EEPROM limits, pack protection board, buzzer) plus lift detection and a thermal ladder.

## 13. The 5 biggest risks to check BEFORE the full parts order

1. **No charging path.** Decide the contact position and its CAD now (the battery bay and door define it). Without a dock the pet works about 35 minutes at a time. Test the dock with a stand-in (a dummy weight and 4 pogo pins) before the shell is printed.
2. **Heat in the closed shell at 35-40 C ambient** (PLA softens at 55-60 C; servo cutoff about 70 C; the Radxa's real draw is unknown). Run a closed prototype with the Radxa, camera and two bucks under load and log temperatures. Choose PETG or ASA before buying filament.
3. **Radxa ZERO 3W bring-up unknowns:** six hardware-PWM overlays, `/dev/watchdog`, the shared BNO055/INA219/MPR121 I2C bus, the camera lens-board fit (`electronics.md:114`). Order a **bring-up kit first** (Radxa, FE-URT-1, two servos, BNO055, INA219, one battery), test these, and order the rest afterwards.
4. **The FE-URT-1 and the bus at 1 Mbps.** Time 1000 sync reads for the 99th percentile and error rate; if the CH340 adapter jitters, change adapter before buying 12 servos. Also confirm the STS3032's protection-register addresses, because the code uses the STS3215 table.
5. **Power-loss and brown-out behaviour.** The BMS cutoff (`BOM.md:53`) kills the Radxa without a shutdown, and the 5 V regulator can sag under servo stalls (the software stops at 4.6 V bus sag, `electronics.md:170-171`). Pull the battery during an SD write with a read-only root and see whether the card survives. Measure the real Radxa-plus-camera power too: it moves the runtime table more than anything else.
